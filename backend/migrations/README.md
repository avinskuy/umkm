# Migrasi Database

Direktori ini berisi migration SQLx berversi. Migration Identity Core yang tersedia:

- `20261121170000_create_identity_accounts.sql` — membuat `users` dan `user_identities`, constraint lifecycle/role/kontak, unique partial index reservasi kontak, trigger immutability, transisi lifecycle 30 menit/30 hari, pemeriksaan metode autentikasi, serta fungsi `create_client_user` yang hanya menerima role Business Owner atau Investor.
- `20261122100000_create_identity_verification.sql` — membuat `verification_sessions`, `verification_challenges`, `otp_verification_attempt_events`, dan `otp_delivery_events`, termasuk state constraints, batas umur challenge 10 menit, satu challenge pending per sesi, binding recovery pra-pemilihan akun, serta indeks event lintas sesi.
- `20261122110000_create_identity_sessions.sql` — membuat `sessions` dengan hash token SHA-256 unik, batas absolut 30 hari, batas idle 7 hari, rotasi token, pencabutan individual, metadata perangkat minimum, serta pencabutan otomatis saat status lifecycle akun tidak lagi aktif.
- `20261122120000_create_account_recovery.sql` — membuat `recovery_contacts` dengan relasi lintas akun yang diizinkan dan deduplikasi per akun, `account_recovery_cases` dengan pemilihan target setelah verifikasi, serta `password_reset_tokens` yang hanya menyimpan hash dan terikat ke kasus/akun.
- `20261122130000_create_identity_audit_events.sql` — membuat `identity_audit_events` append-only dengan actor/subject, action/outcome/reason code, korelasi request, metadata JSONB terbatas, serta perlindungan terhadap UPDATE, DELETE, dan TRUNCATE.

Migration 0001 menyediakan identitas akun dan provider identity. Migration 0002 menyediakan skema verifikasi; runtime OTP, provider, abstraksi key provider, dan enforcement rate limit masih belum diimplementasikan. Batas kebijakan lintas sesi ditetapkan maksimal lima kegagalan per kontak dalam jendela bergulir 60 menit, tetapi enforcement baru berlaku setelah runtime transaksi PostgreSQL diimplementasikan. Migration 0003 menyediakan penyimpanan sesi autentikasi, tetapi belum menyediakan endpoint login/logout, validasi cookie, middleware autentikasi, atau integrasi runtime. Migration 0004 menyediakan skema kontak pemulihan, kasus pemulihan, dan token reset; runtime tetap wajib mencocokkan kontak terverifikasi dengan akun target, menjalankan pemeriksaan risiko, menerbitkan/mengonsumsi token secara atomik, memperbarui password, mencabut sesi, dan menulis audit event. Migration 0005 menyediakan tabel audit dan perlindungan append-only, tetapi backend belum mengirim event dan belum memiliki grant runtime. Batas idle 7 hari dan absolut 30 hari tetap harus diperiksa pada setiap permintaan oleh backend; opsi ingat perangkat tidak mengubah batas tersebut. Migration tidak membuat role database atau membuka grant runtime. Bootstrap terpisah memberi aplikasi hanya EXECUTE pada `create_client_user`, INSERT audit, dan EXECUTE validator metadata; tabel identitas lainnya tetap tanpa akses langsung aplikasi. Hak akses Admin/audit reader dan CRUD domain lain belum dibuka.

Migrasi dijalankan secara eksplisit melalui `database::migrations::run(&pool)`. HTTP server belum menjalankan migrasi atau menginisialisasi database pada startup. Migration 0001–0005 belum dijalankan terhadap database produksi dan tidak boleh dianggap sebagai aktivasi fitur registrasi/login atau pemulihan akun.

Provisioning principal PostgreSQL berada terpisah dari SQLx migration di `backend/database/bootstrap/`. Jalankan `001_create_principals.sql` sebagai DBA pada database khusus sebelum migration, lalu jalankan migration sebagai `usahapintar_migrator`. Setelah migration 0001–0005 selesai, jalankan `002_identity_core_grants.sql` sebagai DBA; skrip memverifikasi ownership non-superuser sebelum memberi EXECUTE pada fungsi SECURITY DEFINER. CI menguji bootstrap dengan DBA sementara, migrator non-superuser, dan login aplikasi terpisah.

Pengujian PostgreSQL untuk migration, invariant identitas, dan privilege principal berada di `backend/tests/postgres.rs`. Gunakan database sementara yang dapat dibuang, bukan database produksi.

Jangan pernah mengubah migration setelah diterapkan pada database bersama. Perubahan skema berikutnya harus menggunakan migration baru dengan versi SQLx berikutnya.
